**QA-ROOM01 / Phase2 room movement is not exposed.** PHONE_APP_PLAN's original Phase2 explicitly includes moving generic rooms. The current UI offers numeric origins only while adding a room; existing Room dimensions has width/depth/ceiling, and an empty-plan drag pans the view. The domain has room-polygon, but its only source references are the command declaration/handler/validation, with no screen/controller call site. This is a source/UI capability inventory, not a failing implemented move gesture. Before claiming Phase2complete, provide a coherent existing-room movement route and verify topology/openings/finishes/contained-item policy,collision,recovery and one-command Undo. Exact control design is an implementation proposal; do not add a redundant persistent button merely to satisfy the inventory.

**Boundary measurement follow-up:** ARCHITECTURE's proposed source-adapter example keeps clear interior dimensions and extrudes thickness outside the finished face. Current renderer instead places half a wall inside the polygon and domain/UI use that logical boundary. The concrete collision above must be fixed regardless of which canonical convention is retained. Separately reconcile/document clear interior inputs/readouts and both-face endpoints; do not silently redefine or resize saved projects to hide the mismatch. For a logical5m span with12cm walls at both ends, the current rendered clear gap is4.88m before trim. This architectural consistency issue needs an explicit implementation resolution, not a claim that extra padding alone proves measured-room parity.
